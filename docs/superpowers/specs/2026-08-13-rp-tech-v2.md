# RP Tech v2 — Spec

**Fecha:** 2026-08-13
**Reemplaza:** `rp-tech_final` (diagnóstico en `_diagnostico/`)

## 1. Qué es

Tienda online de accesorios tecnológicos para RP Tech (Perú). Tres superficies:

1. **Catálogo público** — fichas de producto completas, búsqueda, filtros, página de detalle por producto.
2. **Carrito → pedido por WhatsApp** — el cliente arma el carrito en el sitio; al confirmar se abre WhatsApp con el pedido completo redactado. **No hay pasarela de pago.**
3. **Panel de administración** — CRUD de productos y gestión de stock, con autenticación real del lado del servidor.

Fuera de alcance: pasarela de pago, cuentas de cliente, estados de pedido, envíos, emails transaccionales, portal de vendedores.

## 3. Errores del sistema anterior que este spec debe cerrar

Cada uno de estos es un requisito, no una sugerencia. Referencia: `_diagnostico/`.

| # | Error anterior | Requisito de v2 |
|---|---|---|
| R1 | 4 catálogos contradictorios (products.json, seed SQL, README, localStorage) | **Una sola** fuente de verdad: tabla `products` en Postgres |
| R2 | Stock descontado 2 veces (navegador + servidor), read-modify-write | Descuento **atómico** en Postgres vía función `SECURITY DEFINER`, un solo actor: el servidor |
| R3 | `fs.writeFileSync` sobre `products.json` en Vercel (read-only) | Cero escrituras a filesystem en runtime |
| R4 | `costo` expuesto en `GET /api/inventario` con CORS `*` | El serializador público **elimina** `costo`; test que lo verifica |
| R5 | PIN `1234` en `NEXT_PUBLIC_`, auth solo en cliente | Supabase Auth (email + password), verificada en `proxy.ts` y en cada mutación del servidor |
| R6 | Mismo PIN para vendedor y admin | Un solo rol `admin`; sin portal de vendedores |
| R7 | Servidor aceptaba el `total` calculado por el cliente | El servidor **recalcula** todo precio y total desde la base |
| R8 | `cantidad` negativa inflaba el stock | Zod en todo input + `CHECK (stock >= 0)` en la base |
| R9 | SKU generado con `products.length + 1` → colisiones y renumeración | SKU inmutable, `UNIQUE`, definido por el admin |
| R10 | RLS `FOR ALL USING (true)` con anon key pública | `anon` solo `SELECT` de productos activos; toda escritura vía `service_role` en el servidor |
| R11 | Sin página de detalle → 0 páginas indexables | `/producto/[slug]` renderizada en servidor, con metadata y JSON-LD |
| R12 | `<img>` crudo, 2.8 MB por imagen | `next/image`, imágenes comprimidas a ≤300 KB |
| R13 | Errores silenciados en `console.warn` + `success: true` | Todo fallo se propaga al usuario; nada de éxitos falsos |
| R14 | 0 tests, 0 CI | Vitest en dominio y serializadores; GitHub Actions con typecheck + lint + test |
| R15 | 4 servicios externos (Sheets, Drive, UploadThing, Supabase) | Solo Supabase |
| R16 | `googleapis` completo en el bundle (9.96 MB) | Sin dependencias sin usar; presupuesto de bundle revisado |

## 4. Modelo de datos

### `products`

| Columna | Tipo | Notas |
|---|---|---|
| `id` | `uuid` PK | `gen_random_uuid()` |
| `sku` | `text` UNIQUE NOT NULL | Inmutable, lo fija el admin (ej. `26002`) |
| `slug` | `text` UNIQUE NOT NULL | Para la URL, ej. `audifonos-damix-m20-tws` |
| `nombre` | `text` NOT NULL | |
| `descripcion_corta` | `text` | Una línea, para la card |
| `descripcion_larga` | `text` | Markdown plano, para la ficha |
| `marca` | `text` | REDD, ROMAX, Halion, Apple, HyperX, Damix |
| `modelo` | `text` | RD-2119C, HA-M105, … |
| `especificaciones` | `jsonb` | `[{"etiqueta":"Potencia","valor":"75W"}]` |
| `categoria_id` | `uuid` FK | |
| `precio` | `numeric(10,2)` NOT NULL | Precio de venta, IGV incluido |
| `costo` | `numeric(10,2)` | **Nunca sale al público** |
| `stock` | `int` NOT NULL DEFAULT 0 | `CHECK (stock >= 0)` |
| `stock_minimo` | `int` DEFAULT 3 | Para alertas en el admin |
| `bajo_pedido` | `boolean` DEFAULT false | Visible sin control de stock |
| `activo` | `boolean` DEFAULT true | Oculta del catálogo sin borrar |
| `garantia_meses` | `int` | |
| `created_at` / `updated_at` | `timestamptz` | `updated_at` por trigger |

### `product_images`
`id`, `product_id` FK CASCADE, `storage_path`, `alt`, `orden` int, `es_principal` bool.
Un producto tiene N imágenes; exactamente una principal.

### `categories`
`id`, `slug` UNIQUE, `nombre`, `orden`.
Categorías iniciales: Audífonos · Cables · Cargadores · Powerbanks · Cómputo · Accesorios Auto.

### `orders` + `order_items`
Se registra el pedido **antes** de abrir WhatsApp, para tener trazabilidad y descontar stock.
`orders`: `id`, `codigo` (ej. `RP-2026-0001`), `cliente_nombre`, `cliente_telefono`, `distrito`, `referencia`, `subtotal`, `estado` (`pendiente` | `confirmado` | `entregado` | `cancelado`), `created_at`.
`order_items`: `id`, `order_id` FK, `product_id` FK, `sku`, `nombre` (copia histórica), `precio_unitario` (copia histórica), `cantidad`.

**Los precios se copian al item.** Si mañana sube el precio, el pedido viejo conserva el que se cobró.

### Sin variantes en v1
26003 y 26006 vienen en negro y blanco. En v1 se documenta el color disponible en `especificaciones`. Las variantes con stock independiente quedan para v2.

## 5. Reglas de negocio

1. **El precio siempre lo pone el servidor.** El carrito del cliente solo envía `{sku, cantidad}`. El servidor busca el precio en la base y calcula el total. Nunca se confía en un total del cliente. (R7)
2. **El stock se descuenta atómicamente** en una única transacción al crear el pedido. Si algún item no alcanza, **todo** el pedido falla y se le dice al cliente qué producto se quedó sin stock. (R2)
3. **Un producto con `stock = 0` y `bajo_pedido = false`** se muestra agotado y no se puede añadir al carrito.
4. **`bajo_pedido = true`** ignora el stock: siempre se puede pedir.
5. **El costo nunca sale del servidor** hacia una respuesta pública. (R4)

## 8. Criterios de aceptación

- [ ] `GET` público de productos no contiene la palabra `costo` en ninguna respuesta — test automatizado
- [ ] Dos pedidos simultáneos del último item: uno se confirma, el otro recibe error de stock — test de concurrencia
- [ ] `POST` a cualquier ruta de admin sin sesión responde 401 — test
- [ ] Un pedido con precio manipulado en el body se registra con el precio real de la base — test
- [ ] `/producto/[slug]` responde HTML con el nombre y precio del producto sin ejecutar JS — `curl` lo demuestra
- [ ] `npm run build` pasa sin errores de tipos ni lint
- [ ] Ninguna imagen del catálogo supera 300 KB
